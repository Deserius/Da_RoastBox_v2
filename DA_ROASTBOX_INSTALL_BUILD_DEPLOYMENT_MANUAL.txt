READ FIRST — WHAT THIS GUIDE CAN AND CANNOT PROMISE
A terminal is a text window for entering commands. PowerShell is the Windows
terminal used below; Bash is a common macOS/Linux terminal. A repository is a
versioned project folder, a dependency is an installed package, and deployment
means putting the app on a server so other people can use it. The frontend is
the page users see; the backend is its Python server. An API connects them.

The source archive does not include customer databases, real API keys, provider
accounts, environment files, installed packages or generated private media.
This is not proof that a real cloud account, payment, email, Google login,
mobile build or production launch works. Test live services only after approval;
AI and voice tests may cost money. Preview login is for private testing, never a
production identity system. Read the other two root manuals for architecture
and AI changes, and docs/LOCAL_INSTALL.md, DEPLOYMENT.md and INTEGRATIONS.md.

1. BEFORE YOU START
-------------------
You need a 64-bit computer, reliable internet and several GB of free disk.
The installer downloads dependencies and a large MongoDB archive. A local
preview uses port 3000 for the frontend, 8001 for API and 27017 for MongoDB;
other software must not occupy them. Supported Python is 3.11–3.13, recommended
3.13: https://www.python.org/downloads/ . On Windows select the option to add
Python to PATH. A code editor such as https://code.visualstudio.com/ makes
editing easier. Git is a change-history tool: https://git-scm.com/downloads .
A GitHub account at https://github.com/ is optional for local use, useful for
hosting. Never install or run a source archive from inside the ZIP viewer.

install.py downloads project-local Node 22.23.4, Yarn 1.22.22 and MongoDB 8.0.34
with pinned checksums; it does not require a global Node installation. For
manual/npm/Capacitor work install a suitable Node version from
https://nodejs.org/ . MongoDB Community is from https://www.mongodb.com/try/download/community
and Atlas is at https://www.mongodb.com/atlas . On supported platforms the local

password, database URI, JWT_SECRET, session token or screenshot of them.

2. INSTALL FROM A SOURCE ZIP — WINDOWS POWERSELL
--------------------------------------------------
1. Extract the entire archive to a writable folder. Open its project folder; it
   must contain install.bat, frontend and backend. The exact folder name depends
   on how the ZIP was extracted. No public repository URL was supplied.
2. In File Explorer, click the folder address bar, type powershell and press
   Enter. This opens PowerShell in that folder. Verify:
      Get-ChildItem install.bat,frontend,backend
   You should see all three names. If not, open the correct folder first.
3. Install Python 3.11–3.13 if absent. Check:
      py -3.13 --version
   If you have another supported version use that instead. The Windows
   current launcher automatically prepares verified per-user Python without winget; approve required Windows permissions.
4. Install the project:
      .\install.bat
   The installer creates .venv, downloads checked local tools, installs
   frontend/backend packages and creates backend/.env and frontend/.env ONLY
   if missing. It can take several minutes. Read any errors; do not disable
   checksum checks. Existing .env/data are retained, not reset.
5. Start it:
      .\start.bat
   Keep the terminal open. Wait until the frontend finishes compiling, then open
   http://localhost:3000 . Close by pressing Ctrl+C in that terminal. Only
   child processes launched by this launcher are stopped; an already-running
   MongoDB is not stopped.
6. Skip/watch the intro and accept the 18+ statement. On a freshly generated
   private development config choose Explore the preview. This is a disposable
   account, not a production login. Browsing requires no AI key.
7. Verify the backend separately in PowerShell:
      Invoke-RestMethod http://localhost:8001/api/health
   Expect a status and version. Optional shallow diagnostics:
      Invoke-RestMethod http://localhost:8001/api/diagnostics
   An optional provider can show unconfigured. Do not add ?deep=true without
   explicit approval: that endpoint contacts external providers and can cost.
8. For real generation, configure a supported provider key securely or use a
   user key in Settings; generation and uncached voice previews can be billed.
   Default preview hosted AI is disabled. Do not expose a preview on the public
   internet. Production requires a separate review described below.

If using an existing database rather than downloading MongoDB:
  .\install.bat --skip-mongodb
Then edit backend/.env in a private editor and set MONGO_URL and DB_NAME to
that already running server. Do not paste the URI into chat or logs. Run
.\start.bat. A remote/authenticated server is not automatically started.

3. CONFIGURATION, RUNNING AND RESTARTING LOCALLY
-------------------------------------------------
An environment file is private configuration, not source code. Templates:
backend/.env.example and frontend/.env.example. The installer creates real
files if missing; NEVER overwrite an existing real .env blindly. For a manual
configuration, first back it up privately; copy only if a file does not exist:
  if (-not (Test-Path backend\.env)) { Copy-Item backend\.env.example backend\.env }
  if (-not (Test-Path frontend\.env)) { Copy-Item frontend\.env.example frontend\.env }
Edit backend/.env in a private editor. MONGO_URL, DB_NAME and a long persistent
JWT_SECRET are required. Prefer the installer-generated random secret; never
paste one into documentation. STORAGE_BACKEND=local is appropriate for a
private standalone preview. For production, configure private durable storage.
Set optional provider flags and secrets only when needed; see Developer Notes
section 6. Keep ALLOW_DEV_LOGIN, ENABLE_PREVIEW_LOGIN, ALLOW_PREVIEW_HOSTED_AI,
ALLOW_SOURCE_DOWNLOAD false for production. Do not commit either real .env.

The frontend makes same-origin /api calls. The local launcher sends them to its
API_PORT via API_PROXY_TARGET; default is 8001. The API log and frontend log
appear in the launch window; don't paste sensitive output publicly. For new
ports in PowerShell (only in this session):
  $env:PORT = "3100"
  $env:API_PORT = "8101"
  .\start.bat
Then use http://localhost:3100 and http://localhost:8101/api/health. To clear
these temporary variables in that terminal: Remove-Item Env:PORT,Env:API_PORT.
Closing the shell also clears its temporary environment. Press Ctrl+C, wait for
shutdown, then run .\start.bat again to restart. The installer is not required
on each restart. Never run a second API instance against the same active reel DB.

Advanced manual split startup (not needed after the normal launcher): ensure
Mongo is already reachable and dependencies/.env exist. In one PowerShell in
project root:
  Set-Location backend
  ..\.venv\Scripts\python.exe -m uvicorn server:app --host 127.0.0.1 --port 8001 --workers 1
In a second PowerShell at project root, using global Node + Corepack/Yarn:
  Set-Location frontend
  $env:API_PROXY_TARGET = "http://127.0.0.1:8001"
  corepack yarn start
The installer stores its own Node/Yarn in .cache/local-tools; if Corepack is not
available, use start.bat rather than assuming a global executable. Do not bind
MongoDB publicly or enable arbitrary dev login. Server restart is required for
backend config/catalog changes; React dev server handles most source edits.

4. PRODUCTION BUILD AND VERIFICATION
--------------------------------------
A development server is for editing, not public hosting. A production build is
optimized frontend static files, output to frontend/build. From a configured
PowerShell with global compatible Node/Corepack in project root:
  Set-Location frontend
  corepack yarn install --frozen-lockfile --non-interactive
  corepack yarn build
  Test-Path .\build\index.html
  Set-Location ..
Expected: build compiles and Test-Path returns True. The source uses CRA/CRACO;
frontend/package.json script is yarn build. If no global Corepack, the included
Dockerfile performs the production build with pinned Node/Yarn. Never copy an
API secret into a REACT_APP_* variable: all of those are public build output.

Dockerfile builds the frontend and Python backend into one image; FastAPI serves
the built site and /api when FRONTEND_BUILD_DIR=/app/frontend/build. The Docker
entrypoint drops privileges and uses one Uvicorn worker. Production server needs
real private MONGO_URL, DB_NAME and stable JWT_SECRET, HTTPS, persistent private
media, correct APP_BASE_URL, appropriate sign-in and provider configuration.
The Blueprint sets local media at /var/data/roastbox on a persistent disk.
One worker and one instance only: reel startup recovery is not multi-worker
safe. The container's audio_cache is temporary and can be regenerated from
backing media; do not confuse it with persistent original audio. Run isolated
backend tests and safe health checks before release. No production launch is
verified merely because a build succeeds.

5. GIT AND GITHUB WITHOUT LEAKING SECRETS
-------------------------------------------
Git remembers changes; GitHub hosts a repository online. The source archive may
not have a .git history. First make a PRIVATE backup of the original folder and
separate database, media and JWT_SECRET. On github.com create a private empty
repository under your own account. Copy its real HTTPS or SSH URL; no URL is
provided with this project. In PowerShell at project root:
  git --version
  git status
If it says not a Git repository, initialize it:
  git init
  git branch -M main
Before staging anything inspect .gitignore and:
  git status --short --untracked-files=all
Never add backend/.env, frontend/.env, .data, .cache, .venv, node_modules,
private media, generated customer audio/images, logs, backups, session tokens
or workspace memory. Review .gitignore for your environment; it is not a
complete security scanner. Use the sanitized source ZIP or an allowlist of
reviewed files. Verify ignored paths without printing their contents:
  git check-ignore backend/.env frontend/.env
Stage individual known-safe files or folders, review and commit:
  git add README.md backend frontend docs scripts Dockerfile render.yaml
  git diff --cached --stat
  git diff --cached
  git commit -m "Initial reviewed Da RoastBox source"
If any sensitive file appears, unstage it before commit:
  git restore --staged <PATH-TO-REMOVE>
Replace the placeholder with the actual path. Inspect binary assets and large
files too; text scans cannot detect secrets in images/audio. If sensitive data
was already committed, revoke/rotate it and get help cleaning history; deleting
a later file is not enough. Do not push until reviewed.

To connect the private GitHub repository, replace the placeholder:
  git remote add origin <YOUR-PRIVATE-REPOSITORY-URL>
  git push -u origin main
Authenticate in Git's browser/credential helper when requested; do not put a
password or token in a command. Later: git status; git diff; git add <reviewed
path>; git commit -m "Describe update"; git push. Before git pull, commit or
back up your uncommitted changes. For a safe rollback, use git log --oneline,
make a new branch from a known commit, verify it in an isolated environment,
then deploy by your host's rollback process; do not run git reset --hard without
a backup. A Git repo does not back up MongoDB, private media or JWT_SECRET.

7. DATABASE, MEDIA, BACKUP AND RESTORE
----------------------------------------
A database stores structured account, show and payment records; media storage
holds the separate images/audio/video. Atlas is one option, not included in a
source ZIP. For production, choose a secured MongoDB host, enable TLS and
restrict network access and user permissions. Set MONGO_URL and DB_NAME only
in the private service environment. See docs/DEPLOYMENT.md for Atlas access.

Backups require THREE separate pieces: (1) MongoDB backup using your provider's
encrypted backup/snapshot/PITR tools; (2) a private encrypted backup of media
under LOCAL_STORAGE_DIR (or the configured object store); (3) a separately
secured backup of stable JWT_SECRET and other necessary deployment settings.
The source Git repository is a fourth, separate backup. Follow your provider's
backup docs instead of pasting a URI/password into a shell command. Set backup
schedules, access control, retention, and alerts. Test a restore by creating a
separate empty database/storage and pointing a separate offline test deployment
at them; verify users, shows, photos, audio and key decryption. Do not restore
onto live data without a maintenance plan and a tested rollback. Local preview
data is in .data/mongo/ and backend/local_storage/ by default; for a consistent
file copy stop the launcher/database cleanly first. Do not delete them as a
troubleshooting shortcut. Remote database password rotation needs coordinated
updates to the host secret; JWT_SECRET rotation can make BYOK data unreadable.

There is no migration framework or complete automatic user-data retention policy
in source. Schema/index changes and deletion policies need explicit code,
privacy/legal review, tested migration and backup. No public URL should point
directly at the private storage directory or bucket. Keep disk capacity and
failure alerts monitored. Render ephemeral container storage disappears on
redeploy; only the mounted volume survives and needs separate backup.

8. TROUBLESHOOTING — SYMPTOM / CAUSE / FIX / VERIFY
------------------------------------------------------
A. App won't start
SYMPTOM: terminal exits or page cannot load. CAUSE: wrong folder, dependency,
port, config or database. FIX: 1. Open folder containing start.bat. 2. Read
last safe error lines; check Python and run installer again (preserves data).
3. Check backend/.env exists without displaying its contents. 4. Check ports.
VERIFY: launcher compiles; http://localhost:3000 and /api/health respond.

B. Missing dependencies
SYMPTOM: module not found / command not recognized. CAUSE: incomplete install,
network failure or wrong Python. FIX: 1. Confirm supported Python. 2. Run
.\install.bat again (or ./install.sh). 3. Read checksum/network errors; never
bypass checksum. VERIFY: successful installer and launcher startup.

C. Missing environment variables
SYMPTOM: startup says MONGO_URL, DB_NAME or JWT_SECRET missing. CAUSE: missing
or empty backend/.env. FIX: 1. Check file exists. 2. Run installer if absent;
otherwise edit it privately, filling required values and preserving old secret.
3. Restart. VERIFY: /api/health responds and logs show startup complete.

D. Invalid provider key / AI or voice failure
SYMPTOM: unavailable, unauthorized or payment/quota error. CAUSE: disabled
provider, invalid key, insufficient credits, unavailable model/voice, network
or access rights. FIX: 1. Check Settings and shallow diagnostics without
revealing keys. 2. Check provider dashboard quota and configured model. 3. Use
mock tests; only attempt live generation after owner approval and cost limits.
4. Check logs for safe error category. VERIFY: mocked checks pass, then an
approved small synthetic live test produces complete script/audio. Local
rejection may still be billed by provider even if app credits are not charged.

E. MongoDB failure
SYMPTOM: startup/diagnostics reports database unreachable. CAUSE: server off,
port, network allowlist, TLS or credentials. FIX: 1. Check local launcher and
.data/mongo-27017.log. 2. For Atlas verify network rules and account privately.
3. Use secured current URI in backend/.env or host environment; don't print it.
VERIFY: shallow diagnostics reports Mongo ping successful.

F. Frontend cannot reach backend / CORS
SYMPTOM: page loads but catalog/auth fails. CAUSE: wrong proxy/API URL, backend
offline or origin denied. FIX: 1. Open /api/health via the same origin. 2. For
local launcher verify API_PORT and API_PROXY_TARGET match. 3. For split hosting
configure only exact trusted HTTPS CORS_ORIGINS and rebuild public frontend API
URL. 4. Inspect browser network/console without copying session headers.
VERIFY: health through site origin and signed-in catalog request succeeds.

G. Port already in use
SYMPTOM: launcher reports port 3000/8001 occupied. CAUSE: another program.
FIX: 1. Stop only the known app using it. 2. Or set PORT and API_PORT to unused
values as in section 3. 3. Restart. VERIFY: new URLs load and health responds.
Avoid killing unknown processes or deleting database files.

H. Build failure
SYMPTOM: yarn build reports dependency or memory errors. CAUSE: wrong Node/Yarn,
missing network, low memory or code error. FIX: 1. Verify supported Node and
Corepack. 2. Reinstall using locked yarn file. 3. Read first error, fix in a
branch. 4. Use Docker/Render build if appropriate. VERIFY: build/index.html and
successful build log; run tests. Never commit node_modules or build artifacts.

I. Deployment failure or crash
SYMPTOM: host deploy fails or health check times out. CAUSE: bad build, missing
runtime variables, inaccessible Mongo or insufficient RAM. FIX: 1. Read build
and service logs. 2. Confirm Dockerfile/root and private environment values.
3. Check DB network/TLS and persistent disk. 4. Roll back safely if necessary.
VERIFY: HTTPS site loads, /api/health works and /api/diagnostics shows Mongo.

J. Audio silent or inconsistent
SYMPTOM: captions work but no sound, or different apparent loudness. CAUSE:
autoplay restriction, provider error, device mute, unavailable file or mix.
FIX: 1. Tap play/resume, check device/browser volume and theater crowd slider.
2. Check safe media errors, sign-in/share authorization and provider status.
3. Run offline voice and crowd tests. 4. Listen on real devices after approval.
VERIFY: sample and fixture show play with clear speech. Voice mastering helps,
but cannot guarantee equal perceived loudness or provider delivery quality.

K. Missing image or reel
SYMPTOM: photo not shown or reel fails. CAUSE: oversized/invalid image, private
storage failure, revoked share, disk full or FFmpeg failure. FIX: 1. Use JPEG,
PNG or WebP, <=8 MiB each, <=25 MP; max 4. 2. Check auth and storage/disk.
3. Inspect reel job state and refund; don't retry blindly after lost response.
VERIFY: fixture image displays and offline reel smoke completes.

L. Mobile layout / sign-in
SYMPTOM: clipped buttons, OAuth loop or muted playback. CAUSE: viewport/safe
areas, popups, native WebView origin or autoplay. FIX: 1. Test browser at
several widths and a real phone. 2. Check callback/HTTPS and cookie behavior.
3. Use a user gesture for sound. 4. See mobile sections for native gaps.
VERIFY: complete sign-in/upload/play/replay/share on actual device.

9. ANDROID — PWA, TRUSTED WEB ACTIVITY OR CAPACITOR?
-----------------------------------------------------
Current source has NO Capacitor configuration/native project and no verified
PWA manifest/service worker/offline support in frontend/public. It is a web
application, not a ready APK. This section is a FUTURE implementation plan,
not a tested conversion. The simplest first step is to use the already-hosted
HTTPS site in Chrome on Android and test it; an installable PWA would additionally
need an appropriate manifest/icons, HTTPS, installability requirements and an
explicit cache/offline design. No offline show generation is implemented.

A Trusted Web Activity (TWA) opens a verified hosted PWA inside Android. It
requires a production domain, Digital Asset Links, Android app signing and PWA
quality. It is viable if the app remains online and the owner controls the
site/domain, but is not implemented or verified here. Capacitor packages the web
build in a native WebView and permits native plugins; it is a reasonable path
for future native features, but NOT a one-command fully functional conversion.
Store rules, testing, security, maintenance and provider callbacks still apply.
See https://capacitorjs.com/docs/getting-started and
https://developer.chrome.com/docs/android/trusted-web-activity/ .

IMPORTANT NATIVE BLOCKERS TO SOLVE BEFORE A FUNCTIONAL RELEASE:
* The bundled frontend runs under a native WebView origin, not your hosted
  domain. Empty REACT_APP_BACKEND_URL points /api at that local origin, where
  FastAPI does not exist. Use an explicitly configured public HTTPS backend and
  carefully allow the actual WebView origin in backend CORS; never use the
  phone's localhost as if it were the developer computer or ship secret keys.
* Several portraits/assets use root-relative /assets paths and CRA BrowserRouter
  assumes web-origin routes. Review public-path handling, embedded assets,
  refresh/deep links, frontend/src/lib/media.js and share URLs on each platform.
* AuthContext constructs managed OAuth callback from window.location.origin;
  a WebView origin may not be accepted by the managed provider. Implement a
  secure external-browser OAuth/deep-link flow with state/PKCE as appropriate,
  verify session and return URLs, cookie/token behavior and provider support.
  APP_BASE_URL and Stripe checkout currently expect a trusted HTTPS origin;
  native origin and deep-link return require design/implementation, not just a
  CORS toggle. Avoid leaking tokens through URLs or logs.
* Store policies for mature content, user-generated material, age screening,
  digital-goods billing and external links differ by region and change over
  time. Existing Stripe web checkout is NOT automatically store-compliant.
  Review https://developer.apple.com/app-store/review/guidelines/ and
  https://support.google.com/googleplay/android-developer/answer/9858738
  with counsel and each store before distribution. App approval is not assured.

9A. ANDROID CAPACITOR EXPERIMENT — USE A BRANCH OR COPY
--------------------------------------------------------
These commands intentionally MODIFY package.json/lockfile and add a native

https://developer.android.com/studio . Capacitor 8 documentation, checked for

Play target API deadlines can change; check official docs at release time.

1. Back up and create a Git branch in a copy. Install global Node 22+ and Android
   Studio; open SDK Manager, install an SDK platform and platform-tools. Android
   Studio includes its appropriate JDK. Configure an emulator or enable USB
   debugging on a test phone. No native changes are part of the present project.
2. Open PowerShell in that copy's frontend folder:
     Set-Location frontend
     node --version
     corepack yarn --version
3. Add matching Capacitor major versions using the existing Yarn package manager:
     corepack yarn add @capacitor/core@^8 @capacitor/android@^8
     corepack yarn add --dev @capacitor/cli@^8
   This downloads packages and changes package.json/yarn.lock. Review changes.
4. Initialize interactively:
     corepack yarn cap init
   Enter app name Da RoastBox and a reverse-domain app ID that YOU control,
   for example replace com.example.roastbox with your own unique registered
   identifier before store submission. Inspect generated capacitor.config.*:
   webDir must be "build" because frontend/package.json builds to build/.
   The following illustrates intended values, not a file already present:
     { "appId": "com.example.roastbox", "appName": "Da RoastBox", "webDir": "build" }
5. Implement and test the blockers above. Set REACT_APP_BACKEND_URL at build
   time to the real separately deployed HTTPS origin (this value is public),
   for example after replacing the placeholder:
     $env:REACT_APP_BACKEND_URL = "https://YOUR-ACTUAL-BACKEND-DOMAIN"
   No placeholder URL will work. Native OAuth/checkout need code changes and
   backend approval even when API calls work. Do not ship cleartext HTTP.
6. Build, add Android once, copy web assets and open native project:
     corepack yarn build
     corepack yarn cap add android
     corepack yarn cap sync android
     corepack yarn cap open android
   cap add creates frontend/android; do it once. Subsequent changes use build +
   sync, not add again. Android Studio may download Gradle/SDK dependencies.
7. In Android Studio select a test emulator/device, press Run and inspect logs.
   For a debug APK choose Build -> Build APK(s) (menu names vary by version).
   Typically output is frontend/android/app/build/outputs/apk/debug/app-debug.apk;

     adb devices
     adb install -r .\android\app\build\outputs\apk\debug\app-debug.apk

   -r replaces that app on the test device. Do not distribute a debug build.

   guidance to add licensed icons/splash assets; existing web intro is separate.
9. For signed release: Android Studio Build -> Generate Signed Bundle/APK;
   create or select a keystore, keep the keystore/password privately backed up,

   Losing signing keys can prevent updates. Follow Play App Signing guidance;
   never commit a keystore. Check Studio output path rather than guessing.
10. Create a Google Play Console account, complete identity, content rating,
    privacy/data safety, mature content and payments review; upload AAB to an
    internal test track first. Verify policy and regional payment requirements
    before launch. There is no guarantee this adult app qualifies for any store.
