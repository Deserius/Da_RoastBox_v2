1. PROJECT OVERVIEW AND DATA FLOW
---------------------------------
Da RoastBox is an adult-oriented React web application for selecting fictional
roasters, uploading subject photographs and context, generating voiced roast
shows or two-persona battles, playing a theater presentation, sharing a show,
and rendering vertical highlight reels. It also provides a persona catalog,
favorites, previews, credit packs and add-ons, account history, optional email
login, managed Google login, a cinematic intro and an illustrated developer
storybook. Clean/adult and heat controls, boundary text and entitlements exist.
40 catalog personas: 25 free and 15 premium as of this inspection.

Frontend: React 19, React Router 7, CRA/react-scripts 5 plus CRACO 7, JavaScript,
CSS and some Radix/Tailwind utilities. Backend: Python FastAPI with Pydantic,
Uvicorn, Motor/PyMongo for MongoDB, Pillow, imageio-ffmpeg and NumPy. An
OpenAI-compatible chat gateway supplies scripts; ElevenLabs/OpenAI TTS supply
speech. MongoDB stores records; local or Emergent object storage stores files.
Real provider access can cost money. A mock test does not prove joke quality,
live service health, safe content, or physical-device behavior.

Browser -> React forms -> Axios frontend/src/lib/api.js -> /api -> FastAPI
backend/server.py -> routes -> validation/access/pricing -> AI writer -> TTS
-> storage + MongoDB -> transcript/media URLs -> browser theater/crowd audio.
Share URLs use a separate revocable public scope; reels render from existing
show media. No server-side image generation or 3D character renderer is part
of the runtime. See the AI manual for precise processing and limitations.

4. BACKEND AND REQUESTS
------------------------
backend/server.py creates the FastAPI app, includes routers under /api, starts
indexes/storage and recovery, optionally serves the compiled SPA from
FRONTEND_BUILD_DIR, and exposes authenticated /api/audio/{filename}. CORS comes
from CORS_ORIGINS. Uvicorn is the HTTP server. One worker/instance is mandatory
with the current reel recovery design. services/roast_engine.py validates image
uploads, normalizes via Pillow, checks credits/entitlements, commits records
and recovers interrupted generations. routes/roast.py and routes/battle.py
orchestrate; services/roast_writer.py builds prompts, calls and parses AI;
voice_orchestrator.py synthesizes; storage.py persists media; audio_mastering.py
levels playback; highlight_reel.py renders video. services/pricing.py defines
credit cost. Logs and friendly errors are in these files; never log private
photos, user inputs, session tokens, credentials or full provider responses.

Background work: routes/reels.py launches an in-process render task and has
startup recovery; it is NOT a durable distributed job queue. Payment, reel and
show marker/ledger recovery does not provide end-to-end request idempotency.
Do not retry a timed-out generation blindly: check recent shows first. For
production, implement a durable ownership-aware queue, request idempotency and
financial reconciliation before scaling or taking live payments.

7. DATABASE, MEDIA, BACKUPS AND STATUS
---------------------------------------
backend/db.py uses Motor AsyncIOMotorClient and creates indexes at startup.
Collections: users (credits, entitlements, encrypted BYOK, favorites), sessions
(revocable), roasts (context, transcript, media references, billing markers),
credit_transactions, payment_transactions, voice_previews,
voice_preview_samples, voice_preview_leases, reels, preview_hosted_usage,
email_credentials, email_tokens, email_auth_rate_limits. Pydantic structures:
User, Session, CreditTransaction, PaymentTransaction, RoastRecord in
backend/models.py; reel/job and auth documents also originate in route code.
TTL indexes on email token/rate-limit and voice lease expiry; user history and
media do NOT have a verified automatic full-deletion policy. Audio read cache is
pruned after seven days at startup; durable originals are separate. Do not claim
this deletes customer data. Design explicit retention/deletion and compliance.

backend/services/storage.py writes private subject images, audio and reels to
local storage or Emergent object storage. /api enforces owner or active-share
scope; do not expose backing disk/bucket directly. Local photo input is bounded
by read_images: at most 4, 8 MiB each, 25 million source pixels, normalized to
JPEG max 1280 pixels and metadata removed. Media and Mongo are separate backups.
Use database provider's encrypted backup/PITR tools and a separately encrypted
copy of persistent media; protect JWT_SECRET independently. Test a full restore
in an isolated environment. No automated migration framework was found: version
schema changes, back up first, write reversible migration and test against a
copy; preserve existing IDs, shares, transaction markers and encryption key.
See deployment manual for non-destructive backup procedure.

Status: core code, bundled art/voice storybook, mocks and offline regressions
exist. Provider configuration, live Google OAuth, real SMTP delivery, real Stripe
webhooks/checkout, a live deployment, adult consent/legal sufficiency and real
mobile-device runs remain NOT VERIFIED. No store-ready app, native 3D engine,
fully reliable semantic content filter, auto-renewing subscription, durable
multi-worker queue or production monitoring/restore service is implemented.
Older purchase entitlements may need reconciliation. Preview accounts are
isolated demonstrations; provider calls are disabled unless allowed/BYOK.

9. SAFE DEVELOPMENT WORKFLOW
------------------------------
1. Make an encrypted backup of source, database, media and JWT_SECRET separately.
2. Use a disposable non-production database, media path and test credentials.
3. In PowerShell open project root; use git status. If no repository exists,
   follow the installation manual's first-time Git steps and inspect .gitignore.
4. Create a branch: git switch -c feature/my-change
5. Change a small coherent area. Never edit .env.example to include real keys.
6. Run focused no-cost tests from the other manuals; then production build and
   an isolated end-to-end check. Review tests before running unknown suites.
7. Review: git status; git diff; git diff --check. Stage only reviewed files.
8. Commit: git add <reviewed-path>; git commit -m "Describe the change"
9. Roll back source by checking out a known commit/branch into a separate
   directory; never run git reset --hard on unbacked work. Database/media must
   be restored separately; test restore before touching live systems.
