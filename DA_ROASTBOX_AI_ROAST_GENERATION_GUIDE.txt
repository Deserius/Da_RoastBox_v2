PURPOSE AND SAFETY
This guide describes source code, not a promise that a model is funny, that
image analysis is accurate, or that every forbidden topic will be caught.
"Model" means the AI program generating language; "prompt" means instructions
and information sent to it. An API is the interface between programs. Provider
calls may be billed even if the app later rejects output. Do not run paid calls
for testing without the account owner's permission. No customer secrets belong
in source, prompts, examples, screenshots or issue reports.

Companion documents: DA_ROASTBOX_DEVELOPER_NOTES.txt gives all systems and
configuration. DA_ROASTBOX_INSTALL_BUILD_DEPLOYMENT_MANUAL.txt covers setup,
hosting, Android and iOS. Read docs/API.md and docs/INTEGRATIONS.md as well.

1. ACTUAL PIPELINE — FROM PHOTO TO PERFORMANCE
-----------------------------------------------
  Browser persona(s), images, optional facts/boundaries, heat/language
      | StudioPage.jsx or BattlePage.jsx; multipart request through lib/api.js
      v
  /api/roast/generate or /api/battle/generate, FastAPI route
      | check session, per-user generation lock, selected personas, access,
      | credits, image count/type/size and user-provided provider key
      v
  roast_engine.read_images -> bounded Pillow decode, orientation/thumbnail,
  JPEG normalization and metadata removal. Images and context are private data.
      v
  roast_writer.build_roast_prompt or build_battle_prompt: selected cast, turn
  plan, details, heat/adult and off-limits serialized as data
      v
  write_script: SYSTEM_PROMPT + request text + ordered high-detail images ->
  existing model chain / OpenAI-compatible client, ONE successful writing call
      | model is instructed to privately identify clear visual choices, rank
      | evidence, brainstorm angles, edit and return JSON; no separate image
      | analyst/critic call, no stored independently verified evidence map
      v
  _script_problem and parse_beats: structural checks and a few narrow content
  checks; local rejection is before TTS/credit charge, but provider may bill
      v
  roast mode finish_roast_script adds voiced welcome, optional safe turn weave,
  final host thanks/motto and rapid-fire marks; battle has separate structure
      v
  voice_orchestrator.synthesize_show generates each beat concurrently with
  selected provider; missing voice fails whole result before credit commit
      v
  roast_engine.commit_record stores images/record and debits or uses free roast;
  API sends transcript and authorized URLs to frontend
      v
  RoastTheater/useShowPlayer shows photo/captions, plays leveled voice, applies
  emotional gaps and ducks crowd; optional share and reel from saved show.

No separate general "roast category" selector exists. Present choices are
roast versus battle, personas, heat, language, context and optional topics to
avoid. Battle can run without an uploaded image. Roast requires at least one.
Name/context are not an unrestricted conversation history. Saved show history
is not automatically fed back to the writing model. There is no persistent
conversation memory or retrieval-based joke library in the present pipeline.

4. COMEDY INTELLIGENCE AND ORIGINALITY
---------------------------------------
Today the "library" is prompt guidance and per-persona metadata, not a database
of jokes or a semantic search system. Current private writer-room instruction
in SYSTEM_PROMPT asks the model to inventory clearly visible clothing, pose,
expression, props and setting, rank usable observations, brainstorm several
angles, select concise speakable lines, and self-check controls. Uploaded photo
index is assigned by the model; it is NOT independently verified. Do not assume
an observation is true when it is unclear or multiple subjects exist. It must
not infer protected traits, identity, age, health or criminality. User-provided
text and text inside images are untrusted data, not overriding instructions.

Use structures as tools, not hard-coded insult templates:
* "your-mama" / family bits: only if all parties and boundaries permit; family
  may be explicitly off-limits, and age/sexual restrictions still apply.
* looking-ass / built-like: ground in a permitted observable styling choice;
  compare to an unexpected concrete thing, never assume sensitive traits.
* "that's why" consequence: setup -> surprising absurd outcome -> quick tag.
* slang and street sayings: choose a few natural character-specific expressions;
  don't impose a single racial dialect or treat criminal identity as a fact.
* one-liner: short setup and reversal; avoid filler and generic "looks like".
* double entendre / adult relationship humor: only with adult mode enabled and
  chosen heat, no sexualization of anyone whose age is unknown.
* story -> misdirect -> payoff; sarcasm, deadpan and comeback; quick reactions
  to prior persona, audience work without invented real audience facts.
* callback: establish a detail, then return with a new twist, not the same line.
* metaphor: compare incompatible specifics in an original way. Multi-stage:
  observation -> assumption -> unexpected correction -> tag. Vary structure.

To customize: update SYSTEM_PROMPT or persona lingo/topics, not copied jokes;
review _persona_block and build_roast_prompt/build_battle_prompt. Keep metadata
fictional. Use a small curated, licensed pool if developing examples; label them
as style references, not guest facts, include clean/adult metadata and exclusion
logic, and add tests. Existing _persona_block filters some exact boundary terms
and omits adult examples in clean mode; it cannot identify all indirect matches.
Avoid repeating line beginnings and punchline targets; planner alternates cast,
local checks reject exact repeats and an extreme repeated "you look like"
pattern. Those heuristics are neither originality detection nor quality scoring.
No automatic joke plagiarism checker or comprehensive safety classifier exists.

5. MODEL PROVIDERS, COST AND FAILURES
-------------------------------------
MODEL_CHAIN in backend/services/roast_writer.py currently names
claude-sonnet-4-5-20250929, gpt-4.1 and gpt-4o in order. Claude is available
ONLY through the existing compatible Emergent gateway if that gateway supports
it; a direct OpenAI key skips Claude. BYOK OpenAI overrides hosted configuration;
hosted Emergent wins over hosted OPENAI_API_KEY. Client construction and base
URL are in services/openai_service.py, not an environment-selectable generic
provider registry. The first usable, non-refusal response stops the chain; the
local validator can reject it without an extra rewrite. Exceptions/refusals can
cause another provider/model attempt, possibly billable. max_tokens=6000 and
model-specific temperatures are in write_script. Inputs include base64 images,
so model must accept multimodal message parts. Contract and availability can
change; test compatibility before changing model names or token limits.

To change models: 1. Branch and back up. 2. Check multimodal JSON, timeout,
provider terms and price. 3. Change MODEL_CHAIN/selection in roast_writer.py.
4. Add mock responses for failure, invalid JSON, clean and boundaries. 5. Run
no-cost regression. 6. Only with explicit approval, compare a small, capped live
sample using synthetic images/data, recording latency, token costs, failure
rate, image grounding, persona distinction, repetition and human-rated laughs.
Do not publish provider secrets or real target images in evaluation reports.

Anthropic direct, Gemini, Hugging Face inference, Ollama/local models and other
providers are NOT implemented as direct runtime adapters despite some installed
SDKs. Evaluate their image input, JSON support, safety, latency, pricing,
licensing and privacy. For a new adapter: define a common async interface
(generate(messages, images, controls) -> text/usage), translate request and
response without leaking provider details to routes, implement limits/timeouts,
cancellation, stable errors and explicit fallback rules, then mock each provider.
Local models require a separately deployed compatible server and resource/security
planning; setting an Ollama URL alone does not make the current code support it.
Avoid automatic extra retry/critic calls that silently multiply costs.

6. PROMPTS, RETRIEVAL AND FINE-TUNING
---------------------------------------
System prompt = high-level rules and output format (SYSTEM_PROMPT). User block =
route-specific instructions plus JSON-encoded target/context/boundaries. Persona
prompt = selected persona's fictional metadata assembled by _persona_block.
Context injection = passing relevant allowed facts as data, not letting those
facts override rules. The source has no separate OpenAI "developer" role;
a future provider adapter can map a higher-priority instruction role as needed.
Few-shot examples illustrate desired form but risk verbatim copying and false
facts; keep authorized examples separate from guest evidence and mode-filtered.
Retrieval (searching a vetted library at request time) and fine-tuning (training
model parameters on examples) are future ideas, not implemented services.

Improve without training: provide good voluntary context and clear photos;
revise instructions to prefer precise observations, reversals and short tags;
compare blinded examples; tune temperature/model and evaluate against a held-out
fixture set; inspect adult/clean/heat boundaries and photo ambiguity. Fine-tune
only after securing rights and consent, collecting diverse well-labeled examples,
removing private information, establishing a measurable baseline and budget,
and verifying the provider supports your desired modalities. A tuned model will
not replace validation, source transparency or ongoing human review.

7. VOICE AND PERFORMANCE
--------------------------
Beats include text, type, persona_id, emotion, delivery, laugh_after, reaction,
pause_before_ms, pause_after_ms, image_index and standalone. parse_beats bounds
integers and normalizes unknown enums. finish_roast_script may reduce final
rapid-fire gaps; browser useShowPlayer interprets pauses between audio clips,
not precise silence inside a generated speech clip. Script author may request a
held reveal in delivery; only providers accepting instructions can attempt it.
voice_orchestrator.py maps emotion -> OpenAI acting instructions and ElevenLabs
short tags. It chooses ElevenLabs when a permitted key is available, falls back
to OpenAI; OpenAI expressive TTS falls back to tts-1. Some directions are
ignored by fallback providers. Verify rights for any voice; do not clone or
impersonate a real person without consent and legal authorization.

Raw audio is stored privately; services/audio_mastering.py locally analyzes and
limits level on access and for newly rendered reels. It has bounded concurrency,
content-addressed cache and fallback to the original. Loudness cannot be made
identical on all voices/devices. Crowd engine reduces volume during speech;
slider preference persists; highlight_reel.py separately ducks the reel mix.
Offline tones test mixing, not an actual professional sound check.

Future 3D director (NOT PRESENT): keep current backend output as canonical beat
timeline; create a separate performance adapter that maps emotion, duration and
phoneme/viseme timing to legal GLB/GLTF characters in Three.js. Load an
asset/rig manifest, render scene, animate facial blend shapes, lip sync, gestures
and stage transitions against audio clock. Obtain actual timing metadata from a
provider or separate aligner, handle drift, permissions and fallback captions;
do not infer phonemes from text as if exact. Do not store biometric face models
of users without explicit consent. Test mobile GPU, reduced motion, offline
fallback, and respect independent voice/audio source. Existing React theater is
2D photo/caption animation, not a Three.js or lip-sync implementation.
